## 1. V2 protocol overview

### 1.1 One HTTP surface, `/api` only

V2 is a **single `HttpApi` tree** built in `packages/protocol/src/api.ts` (`makeDefaultApi` / `makeApi`) and mounted once by `packages/server/src/routes.ts` (`createRoutes`) — there is no second, un-prefixed generation. A mechanical check of every `HttpApiEndpoint` in `packages/protocol/src` + `packages/server/src` at v2.0.18 finds exactly one path that is not under `/api`:

```
GET /auth/connect/:code     packages/protocol/src/groups/server.ts
```

Everything else is `/api/...` or `/api/experimental/...`. So V2 *is* the `/api` generation that the V1 server shipped alongside the legacy unprefixed surface (V1 mounts both: `packages/opencode/src/server/routes/instance/httpapi/api.ts` builds `RootHttpApi + EventApi + InstanceHttpApi + ServerApi + PtyConnectApi`; `ServerApi` is the `/api` one, everything else is unprefixed). Transport is plain HTTP/1.1 + JSON; SSE for the two streams; WebSocket only for PTY (`/api/pty/:ptyID/connect`). No gRPC, no version prefix, no content negotiation — the whole surface is one OpenAPI 3.1 document.

**Practical consequence for cola**: the unprefixed V1 surface that almost every cola call uses *does not exist in V2*. See the delta table.

### 1.2 The event model changed shape underneath the API

V1's protocol was a **message + part** model: `GET /session/{id}/message` returns `[{info, parts}]`, each part is its own row with `type: text|reasoning|tool|file|step-start|…` and a `state` sub-object (`packages/schema/src/v1/session.ts`, `SessionV1.WithParts` at :493).

V2 is **event-sourced with content embedded in the message**: every domain event is declared in `packages/schema/src/event.ts` (`Event.durable` / `Event.ephemeral`) with an explicit durability and a `durable: {aggregateID, seq, version}` envelope, and the read model is `packages/schema/src/session-message.ts` where an assistant message owns `content: AssistantContent[]` — a tagged union of `text` / `reasoning` / `tool` (`AssistantText` :221, `AssistantReasoning` :232, `AssistantTool` :181). Message types are `user | synthetic | system | skill | shell | assistant | compaction | agent-switched | model-switched | location-switched | idle` (`SessionMessage.Info` :281).

So: **"part" is gone as a first-class row.** In V2 only the *tool* content item has an `id` (`AssistantTool.id`, the tool call id); `text` and `reasoning` items have no id at all — which is the same trap as V1 pitfall #9, but for a different reason (V1's parts had a DB column that was not serialised; V2's text/reasoning content items have no id anywhere).

### 1.3 Streaming: one global volatile stream + one per-session durable log

- `GET /api/event` — SSE, `text/event-stream`, **global across every loaded location** ("Subscribe to native events and plugin RPC events across all server locations. Volatile by contract: a slow consumer overflows and fails the stream, and events during disconnection are missed." — `packages/protocol/src/groups/event.ts:47`). Envelope: `{id, created, type, metadata?, location?, data, durable?}` (`packages/schema/src/event.ts:68-150`), plus plugin RPC events as `{type: "rpc.<name>", created, data, location, id}`. Handler: `packages/server/src/handlers/event.ts` — first frame is `server.connected`, then a `: heartbeat` comment every 15 s. Backed by `packages/server/src/event-feed.ts` with a 4096-slot bounded queue that **fails the stream** on overflow.
- `GET /api/experimental/session/{sessionID}/log?after=&follow=` — SSE over the **durable** per-session log: items are `SessionEvent.Durable | EventLog.Synced`, so you can resume from an aggregate sequence (`packages/protocol/src/groups/session.ts`, `session.log`; `packages/schema/src/event-log.ts`).
- The first-party clients use the global stream: `packages/client/src/solid/connection.ts` reconnects with a 45 s idle timeout against the server's 15 s keepalive. V1's own clients had the same shape (`/event`), but V1's `/event` was **filtered per instance/directory server-side**; V2's `/api/event` is not — the consumer must filter on `event.location.directory`.

### 1.4 Permissions and questions

- Permissions: pending list is **per location** at `GET /api/permission/request` → `{location, data: Permission.Request[]}`; answering is **per session** at `POST /api/session/{sessionID}/permission/{requestID}/reply` with body `{decision: "once"|"always"|"reject", message?}` (`packages/protocol/src/groups/permission.ts`). The V1 global `POST /permission/{id}/reply` and V1-dev's `POST /api/permission/request/{id}/reply`-style global answer are gone.
- Questions became **forms**: `GET /api/form` (per location), `GET/POST /api/session/{id}/form`, `GET/DELETE /api/session/{id}/form/{formID}`, `POST /api/session/{id}/form/{formID}/reply` with `{answer: Record<key, string|number|boolean|string[]>}` (`packages/protocol/src/groups/form.ts`, `packages/protocol/src/groups/session.ts`, `packages/schema/src/form.ts`). No `reject` endpoint — cancellation is `DELETE /api/session/{id}/form/{formID}` or an unanswered field. Events: `form.created` / `form.replied` / `form.cancelled`.

### 1.5 Server lifecycle, auth, discovery

- **A password always exists.** `packages/cli/src/server-process.ts:87-97`: if `OPENCODE_PASSWORD` / `OPENCODE_SERVER_PASSWORD` is unset, a `randomBytes(32).toString("base64url")` password is generated; when foreground it is *printed* (`server password ${password}`) and otherwise stored. `packages/server/src/process.ts:57` refuses to start without one ("Missing server password"). V1 served unauthenticated when no password was set (`packages/opencode/src/server/auth.ts`, `required()` + `ServerAuth.Config` defaults to `Option.none()`).
- **Username is hardcoded `opencode`.** `packages/server/src/process.ts:171` — `ServerAuth.Config.of({password, username: "opencode"})`, and `packages/server/src/auth.ts:19-21` `configLayer` always sets `username: "opencode"`. V1 read `OPENCODE_SERVER_USERNAME` from the environment with a `"opencode"` default (`packages/opencode/src/server/auth.ts:13-16`). The v2 docs still advertise `OPENCODE_SERVER_USERNAME` (`packages/web/src/content/docs/*/server.mdx:39`) but no code path in v2.0.18 reads it.
- Same Basic scheme, same `?auth_token=<base64 user:pass>` query fallback (`packages/server/src/middleware/authorization.ts:29-38`). **New**: an HMAC-signed session cookie (`opencode_session_<port>`, 30-day TTL, signed by the server password so rotation revokes sessions) accepted in place of Basic (`packages/server/src/auth.ts:29-56`), redeemable via `POST /api/pair` + `GET /auth/connect/:code`.
- **Discovery is a first-class file.** The managed service registers `{id, version, url, pid, password}` at mode 0600 in the XDG state dir, default filename `service.json` (`packages/cli/src/services/service-registration.ts:15-33`, `packages/cli/src/services/service-config.ts:37-47`; the client-side contract is `packages/client/src/service.ts` `Info`), default port `0xc0de` = **49374** (`service-config.ts:49-52`). `opencode serve` (no `--service`) instead defaults to **127.0.0.1:4096** and walks forward on EADDRINUSE (`packages/server/src/process.ts:151-157`).
- `GET /api/info` is the readiness probe: `{version, pid, urls[], paths:{tmp}}`, HTTP 200 ready / 503 `{code:"service_starting"|"service_stopping"|"service_failed"}` while booting (`packages/protocol/src/groups/server.ts:34-46`, `packages/server/src/process.ts:157-166, 173-208`).
- Storage: one SQLite DB at `<data>/opencode.db` (`packages/cli/src/database-path.ts`), with a one-shot **V1→V2 history migration** exposed at `GET /api/experimental/migration/v1` (`{status: "required"|"running"|"completed"|"error", …}`) and implemented in `packages/core/src/database/v1-migration.bun.ts` (reads the V1 `session`/`message`/`part` tables, preserves ids). Data dir is still `~/.local/share/opencode` via `Global.Path.data` (`packages/util/src/global.ts`).

## 3. Risky / uncertain areas

1. **The unprefixed surface is gone, not deprecated.** I found no compat mount, no feature flag, no `/v1` prefix at v2.0.18 — every non-`/api` `HttpApiEndpoint` is `/auth/connect/:code`. But `packages/core/src/database/v1-migration*` and `packages/schema/src/v1/*` show the team does keep V1 *data* and *schemas* around; a V1-shaped read-only compat mount could still be added in a later 2.x. Treat "V2 = `/api` only" as true at v2.0.18, not as a promise about 2.x.
2. **No version negotiation and no capability probe.** `packages/protocol/openapi.json` declares `security: []` and no `securitySchemes` (the V1 public spec deliberately stripped them — `packages/opencode/src/server/routes/instance/httpapi/public.ts`), so there is no machine-readable way to ask "am I talking to V1 or V2?". The only reliable discriminator is a probe (`GET /api/info` for V2; V1 answers 404) plus `GET /api/session/{id}/message` shape sniffing. Worth designing deliberately.
3. **Discovery is the riskiest single change.** V2 `serve` without a configured password generates a random one and prints it to **stdout** (`packages/cli/src/server-process.ts:93-95`); cola's current `/proc`-env sniff (which relies on `OPENCODE_SERVER_PASSWORD` being in the child's env) will find nothing. The managed-service registration file is the supported path but lives in the XDG **state** dir and is `0600`, written only in `--service` mode. Nobody is under an obligation to keep that file format stable — `Service.Info` is a plain TS type (`packages/client/src/service.ts:52-64`), not a versioned contract.
4. **Username is hardcoded but the docs still say otherwise.** `OPENCODE_SERVER_USERNAME` is documented in v2's own docs but read by no v2.0.18 code path. cola's `username_from_env` will produce a *wrong* username for a V2 server whose env happens to set it. Prefer a probe-and-compare, or just always send `opencode` when the server looks like V2.
5. **The prompt payload lost per-turn model/agent/variant.** This is a behavioural, not just syntactic, change: cola's `/model` + `/think` + `/agent` runtime overrides currently ride on each prompt (`src/opencode/client.rs:335-338`). In V2 they must become session mutations (`POST /api/session/{id}/model|/agent`), which are durable and shared with any other client on the same session — a real semantic change for a multi-user session, and a new race (override → prompt → restore) to design.
6. **Form replaces question with a different answer shape.** Positional `answers: string[][]` → keyed `answer: Record<key, value>`; `options[].label` → `options[].value`; `custom` moves to a per-field flag; conditional visibility (`when`) and `external` fields are new; `reject` is gone. cola's question card (`src/feishu/card/question.rs`) is a positional multi-select UI and cannot be adapted by field renaming.
7. **The event stream is documented as lossy and now global.** `/api/event` "overflows and fails the stream" (`packages/protocol/src/groups/event.ts:47-51`) and carries **every location's** events; V1's `/event` was server-filtered per directory. Any streaming work must filter client-side and reconnect. cola polls today, so this is a "don't get worse" note rather than a blocker.
8. **Part → content is a renderer rewrite, not a rename.** V1 had `step-start`/`step-finish`/`file`/`agent`/`subtask`/`retry`/`compaction` parts; V2 folds most of those into message types (`shell`, `compaction`, `idle`, `retry` on the assistant, `skill`, `system`) and keeps only text/reasoning/tool as `content`. `src/bridge/turn/render.rs` and `src/opencode/wire/legacy.rs` are keyed on V1 part types.
9. **Idle/busy is coarser in V2.** `session.active` gives only `{type:"running"}`; V1's `retry` status (with the `action` prompt cola's snapshot card surfaces) is now the `RetryScheduled` event + the assistant message's `retry` field. Any "waiting on the provider, here's a Retry/Skip button" affordance needs rebuilding.
10. **Unverified by running code.** Everything above is read from source at the two revisions named. I did not boot a v2.0.18 server and diff live JSON, so wire-level details that are only enforced at runtime (e.g. exact `Location.response` deepObject query encoding `location[directory]=`, SSE frame bytes for `log.synced`, the 503 body during migration) are inferred from the schema/handler source and should be smoke-tested before cola's protocol layer is rewritten.

## 4. Open questions

1. **Does cola need to support both protocols simultaneously?** The cheapest path is a `/api`-first client with a V1 fallback (the reverse of today's split), gated by a `GET /api/info` probe. Or pick a minimum server version and drop V1. This decision drives everything else in the delta table. (Owner: whoever owns the protocol ticket on #353.)
2. **What is the supported discovery contract?** Registration file (`service.json` in XDG state, `{id,version,url,pid,password}`), `/api/info` + `/proc` env, or "ask the human to paste `server password …`"? Note the tension with cola pitfall #7 ("never use a private data dir — one store, many clients"): the V2 managed service is a *service* with its own registration, so a V2 server cola starts must be `opencode serve --service` (port 49374), not a bare `serve`.
3. **Does the V1→V2 data migration preserve session ids, or must cola re-map its `SessionStore`?** `v1-migration.bun.ts` reads the V1 `session` table and writes new rows, but I did not trace whether `id` is carried verbatim or regenerated. If regenerated, every chat→session mapping in cola's `SessionStore` breaks on upgrade.
4. **Should cola adopt `/api/event` + `/api/experimental/session/{id}/log` for streaming (replacing polling)?** The durable log with `after=` cursors would give cola reliable catch-up instead of its current poll-and-render; but it is marked *experimental*.
5. **Per-turn model/agent overrides: session mutation, or accept the loss?** If cola must keep `/model` behaving as a per-message override, V2 forces a switch-restore dance around each prompt. Is that acceptable, or should the feature be redefined as "session model" in cola's own terms (with a card/state change)?
6. **Does anything else in the ecosystem still speak V1?** OpenChamber and cc-connect are cola's neighbours; if OpenChamber has a V2 client yet, its retry/permission/message-id semantics would be a useful second reference implementation to copy rather than inventing.
7. **Which of the `/api/experimental/*` routes may cola depend on** (`session/log`, `session/wait`, `session/import|export|stats`, `fs/write`, `migration/v1`)? There is no stated stability policy in the spec beyond the path prefix. If cola needs `wait` (V1 had `POST /api/session/{id}/wait`, now experimental) for its drain logic, that dependency should be recorded as experimental in cola's docs.
