# Session ownership: server is the single source of truth

How cola decides what identity a session has, and which session a thread may use.

## Context

- cola's `SessionEntry` stores a per-thread `name` that duplicates the server's
  `title`. The server auto-generates `title` from the first user message with a
  small model (`ensureTitle`, `packages/opencode/src/session/prompt.ts`) — unless
  the title was already changed. Two names diverge: `/name` only edits the local
  one, and external clients (OpenChamber, CLI) never see it.
- Sessions created outside Feishu on the shared default store are invisible to
  cola's commands: `/list` and `/switch` are scoped to the current thread's store
  entries (`store.list_thread`), and the store only contains sessions cola itself
  created.
- The server exposes normalized, canonical APIs (`GET /session`,
  `GET /session/{id}`, `PATCH /session/{id}`) for listing and renaming — but
  cola's `list_sessions` client method hits the legacy `/api/session` path and is
  dead code.
- Server facts (verified against the running shared store and OpenCode source):
  - Every session has a non-empty `title`: `New session - <iso>` at creation,
    auto-generated by a small model on the first user message if (and only if)
    the title is still the default. Sub-task children keep
    `Child session - <iso>` forever (never auto-titled).
  - A PATCHed title is never overwritten by auto-generation.
  - `GET /session` without a `directory` param lists the **whole shared store**
    (all directories), sorted by `time_created`; with no `limit`, everything.
  - Session-scoped requests (e.g. `POST /session/{id}/message`) route to the
    **session's own directory**, not the caller's (`workspace-routing.ts`:
    `session?.directory || query || cwd`). Adopting a session from another
    directory therefore runs correctly with no special handling.
- Today a thread can hold several sessions (lobby or topic): `/new` and `/dir`
  inside a topic insert a second session into the topic's key. The `CONTEXT.md`
  glossary ("one lobby session per chat", "A Thread contains exactly one
  Session") already disagrees with this reality.

## Decision

- **The server is the single source of truth for session identity.**
  `SessionEntry` drops `name`; every title display and match reads the server.
  The old field is left to serde's default unknown-field handling, so legacy
  `sessions.json` files load unchanged.
- **One session maps to at most one thread at a time.** The invariant is already
  enforced by `set_active`'s session_id dedup. Adopting a session that is mapped
  to another thread is rejected (ADR-0008) unless the user passes `--force`.
- **Topics hold exactly one session** (created by the first message, or by the
  first session-selection command in a never-had-a-session topic). **The lobby**
  (group/p2p top-level) **may hold several**. Session-selection/creation commands
  are rejected inside a topic that already has a session; operation commands
  (`/stop` `/compact` `/agent` `/model` `/autoaccept` `/name` `/restart`
  `/restart-opencode` `/help`) always work.
- **Title policy**: `/new <name>` and `/name <new>` PATCH the server title
  immediately; `/dir <path>` and auto-created sessions leave the default title so
  the server generates one after the first message.
- A session adopted from any directory is executed in its own directory (the
  server routes by session directory); cola copies `directory` from the server's
  `Session.Info` into the entry.

## Why

- One source of truth kills the cola-name/server-title divergence; adoptions and
  renames are visible on every client (OpenChamber, CLI, cola).
- The 1:1 mapping keeps permission-card routing and the external-message poller
  deterministic: a session has exactly one owner thread, so cards and
  notifications go to exactly one place.
- Single-session topics make `get_active` deterministic inside a topic and remove
  the thread-local-vs-global ambiguity from `/switch` (ADR-0008). Multi-session
  stays where it is actually used (the lobby).
- Leaving default titles to the server preserves the AI-generated titles instead
  of substituting basenames or prompts.

## Alternatives considered

- **Mirrored title cache** in the entry, refreshed on access: keeps `/switch`
  thread-local matching network-free, but reintroduces a second copy that can go
  stale (external renames). Rejected in grilling; the server is localhost, so
  fetching on demand is milliseconds.
- **Multi-session topics** (status quo): possible via `/new`/`/dir` inside a
  topic today. Rejected — adds the thread-local-vs-global ambiguity to `/switch`
  and lets `get_active` pick an arbitrary session in a topic.

## Risks / open questions

- Auto-created sessions show the default `New session - ...` (or an id-tail in
  card subtitles) until the server generates the title after the first turn —
  transient, cosmetic.
- Legacy entries keep their `name` field harmlessly; nothing reads it after
  migration. Old entries whose server session 404s are already recreated
  (pitfall #7); unchanged.
- `CONTEXT.md` glossary needs a correction: the lobby may hold several sessions,
  and "A Thread contains exactly one Session" applies to topics only. Update it
  as part of the implementation.
