# Implement Spec (cola)

Cola's adaptation of the upstream `implement-spec` skill (`mattpocock/skills`, `skills/engineering/implement-spec/SKILL.md`). The step structure follows upstream so the two stay diffable; every **[cola]** divergence from it is marked.

You have been given a spec with tickets. The goal is the whole spec implemented, reviewed by the repo's **paired** pass: by default on one **integration branch**, with every ticket **landed linearly**, ending in a single PR; in the spec's **per-ticket** landing mode, one PR per ticket, each revertible on its own.

Communicate with sub-agents through sparse **context pointers** — the spec, tickets, commits, and notes on disk — not restated prose.

[cola] **Landing is linear.** This repo merges a PR by **rebase only**, so no batch branch may ever gain a merge commit. Every landing is a rebase of the ticket branch onto the integration tip followed by `git merge --ff-only`, never `git merge` of the ticket branch. The branch stays merge-commit-free (`git log --merges main..HEAD` empty) and, once the PR exists, rebase-mergeable (`gh api repos/<owner>/<repo>/pulls/<n> --jq .rebaseable` is `true`) — step 8 sequences those two checks. The `merger` sub-agent (`.opencode/agent/merger.md`) owns landings: it lands, it never judges.

[cola] **Two landing modes, named by the spec.** **Integration** (the default) is everything below. **Per-ticket** trades the single PR for revertibility: each ticket gets its own branch off the then-current `origin/main` and its own PR (`Closes #<ticket>`), driven green and — only when a **merge grant the user records in the spec's `## Landing` section** (`docs/agents/issue-tracker.md`, "Specs and tickets") **names that ticket** — merged by the orchestrating session before the next ticket branches. The grant names its tickets (`merges #11, #12, …`); an unnamed ticket stops at its green PR, and so does every ticket when the spec records no grant. Per-ticket mode keeps the frontier at **one ticket at a time** — serial by definition, since nothing may be cut until the previous PR merged — so each PR is cut from the merged tree and its checks and pair cover the union, and no PR stacks on an unmerged one. The mode changes landing only: the gate rounds and their stop predicates, the dossier and the deferred list do not move.

[cola] **Review is the pair, run at every landing.** `/code-review` carries both the two axes and the adversarial pass; *when* it runs, *who* calls it, and how findings route are the binding in `docs/agents/flow.md`.

[cola] **Run to a green PR, then stop.** This is `CONTRIBUTING.md`'s loop: push, open the PR, and drive it to a green required-check set and a passing Codex gate. Stop there — the user verifies and merges; agents never merge, except under a merge grant the spec records (`## Landing`). A gate stop predicate still hands the PR over (`CONTRIBUTING.md` "Reviewing").

## Steps

1. Read the spec and its tickets; build the **task graph** from the native blocking edges and find the ready **frontier**. [cola] Reconcile the spec's open children before dispatching (`issue-tracker.md`, the gh conventions): each one is either in the batch or on a **drop list** with its reason — not `ready-for-agent`, or a blocker outside the batch — and a child in neither is a resolution bug, not a silent omission.
2. (optional) Dispatch an **exploration sub-agent** for whatever the tickets need, saving its notes **outside the repo** (a scratch directory every later sub-agent can read), so implementers focus on implementation rather than exploration.
3. Prepare the integration branch off `origin/main`: `<type>/<spec-slug>`. Do not open the PR yet — a branch with no commits ahead of `main` cannot. [cola] In per-ticket mode there is no integration branch: each ticket's branch is cut from the then-current `origin/main` at step 4, and nothing is prepared up front.
4. Dispatch one `implementer` sub-agent per **frontier** ticket, each in its **own worktree under `.worktrees/`** on its own branch, based on the integration tip (per-ticket mode: the fetched `origin/main`, with the frontier held at one ticket). Each implementer drives `/tdd` and, before reporting, **rebases onto the integration tip** (`git rebase <integration-tip>`; per-ticket mode: `git rebase origin/main`) — never merges it in. Implementers do not review.
5. Land each completed ticket with a **`merger` sub-agent** (linear, per the [cola] landing rule). When a landing unblocks new tickets, dispatch more implementers — that is the concurrency. [cola] A tightly coupled spec whose tickets keep touching the same files runs **serially**: keep the frontier at one ticket at a time, so each landing is reviewed on a settled tip instead of trading conflicts. [cola] In **per-ticket** mode the ticket's branch is pushed as its own PR (step 8) instead of landed on an integration tip, and `merger` is not dispatched.
6. Review with `/code-review` at each landing over that ticket's window, and again over the **whole branch** (`origin/main...HEAD`) once every ticket is in. [cola] In per-ticket mode there is no whole-branch pass: a ticket's window is its PR's `origin/main...HEAD`, and the pair runs there before the PR goes green. A finding goes back to **the implementer that wrote that ticket** — resume its session: it holds the context, so the fix is one round rather than a re-brief. Only a finding the ticket cannot own (a cross-ticket interaction, or a session already gone) goes to a fresh implementer. Re-review at the scope that raised it, per `docs/agents/flow.md` — a same-scope fix round resumes the reviewer sessions that raised the finding (keep their ids from that round, so it re-reads the delta rather than the whole diff), while the whole-branch pass is a new scope and starts fresh reviewers. [cola] Once a ticket's window review has no blocking finding or its blocking findings are fixed, post exactly one progress comment on the ticket — `gh issue comment <n> --body "implement-spec: landed <sha> on <branch> (batch spec #<spec>). review: clean | fixed N findings. blocking: none | <one line>. deferred: none | <one line>."`, where `<sha>` is the ticket's last commit (the window tip, which Resume matches against; per-ticket mode adds the PR number) — and when a later fix extends that window, update the same comment (`gh api --method PATCH repos/<owner>/<repo>/issues/comments/<id> -f body="..."`) rather than adding a second, preserving the `blocking:` and `deferred:` lines already on it and appending new ones. That way an interrupted batch can be resumed from the tracker. That comment is also the batch's sanctioned `/compact` boundary: the ticket is self-contained and everything step 6 accumulated for it is now disposable. Never compact mid-ticket: a live findings thread is session-local. (Integration mode: a ticket-window fix is local and does not push; the whole-branch pair covers every landed ticket. Per-ticket mode commits and pushes the fix to that ticket's PR, and the pair re-runs on the PR's window.) If an interrupted batch resumes and pushes a ticket fix, re-review the adopted tip with the pair first.
7. `git fetch` and rebase the batch branch — the integration branch, or in per-ticket mode the ticket's own — onto the fetched `origin/main`, resolving a conflict by intent (a genuine conflict pauses the batch) — then run the repo's full verification loop (`CONTRIBUTING.md`, "Verification loop") on the **resulting** tree: the one that ships, not the pre-rebase one.
8. [cola] Push. Open exactly **one** PR against `main` whose body closes **every ticket and the spec** (one keyword per number), per `CONTRIBUTING.md` "Pull request rules" and `docs/agents/flow.md`'s "PR body", and post the gate-dossier comment (`<!-- gate-dossier -->`: the rounds spent and the deferred findings — the union of the tickets' and the spec's `deferred:` lines), keeping its comment ID. — [cola] the spec stays open when the drop list named a child the batch did not cover, and the body names that child instead. Then verify the branch is merge-commit-free (`git log --merges main..HEAD` empty) and rebase-mergeable (`gh api repos/<owner>/<repo>/pulls/<n> --jq .rebaseable` is `true`) — that read needs the PR's number to exist, and a conflict with `main` leaves it `false`, so rebase onto `origin/main`, re-run the checks the rebase touched, and push again. [cola] **Per-ticket mode** opens one PR per ticket instead: its body closes that ticket alone (`Closes #<ticket>`) and names the spec as context (`Part of #<spec>`, never a closing keyword), and each PR carries its own `<!-- gate-dossier -->`. The spec's own closing keyword rides the **last** child's PR, once every other child is merged — verify each child's PR is merged with `gh pr list --search 'closes #<child>' --state merged` before writing it — unless the drop list named a child, in which case every PR carries `Part of #<spec>` and the spec stays open. The last PR carries one keyword per number (`Closes #<ticket>, closes #<spec>`), never a bare comma list.
9. [cola] Drive the PR to **green**: `gh pr checks <branch> --required` plus the Codex gate. A red check or a FAIL is a fix round (route it like step 6): fix **all blocking** findings (answer the non-blocking ones and defer them), re-run the pair at the same scope, and push once. The CI gate's rounds run autonomously until a stop predicate holds (`CONTRIBUTING.md` "Reviewing"): fix every blocking finding and push once per round; when a predicate fires, stop without waiting, write the matched predicate and the remaining findings into the dossier, and hand the PR to the user. A PASS with a non-blocking backlog adds those findings to the deferred list too, and whenever the loop ends, a non-empty deferred list becomes a follow-up issue linked from the dossier. A `critical` security or data-loss finding is fixed and pushed in its own round first and is never deferred. Once the required set and the gate are green, freeze the branch — push again only for a real finding (yours or the user's) or a required rebase, and wait for that round's PASS. Then clean up the implementer worktrees. [cola] In per-ticket mode a green PR is merged by the orchestrating session **only when the spec's recorded merge grant names that ticket**: remove the ticket's worktree, `gh pr merge <n> --rebase --delete-branch`, then `git switch main && git pull --ff-only` before cutting the next ticket's branch, so the next PR starts from the tree the merge landed. An unnamed ticket — or any ticket with no grant — stops at its green PR (step 10).
10. Stop at the green PR — the user verifies and merges, except where the spec records a merge grant. [cola] In per-ticket mode the batch ends when the last child's PR is merged and the spec is closed; without a grant it ends at a green PR handover, and the spec stays open for the rest. [cola] On a handover — a stop predicate holds — stop there and hand the decision over (`CONTRIBUTING.md` "Reviewing"), cleaning up or naming the implementer worktrees you keep. [cola] The follow-up issue's body starts with `Deferred from #<pr>`; search `gh issue list --search 'Deferred from #<pr>' --state all --limit 100` before creating one, so a retry adopts the issue an interrupted run already made. [cola] After every round's review posts, PATCH the dossier comment with the full record — the earlier rounds preserved, the new round and any deferral appended; before stopping, make sure the last round is in it. A comment spends no round.

## Guardrails

- The orchestrating session calls the reviewers (`implementer` and `merger` deny `subagent`); the merger only lands.
- One PR per spec, or one per ticket in the spec's per-ticket mode. Never merge, except under a merge grant the spec records for that batch — the user's explicit go-ahead, which `CONTRIBUTING.md`'s agent rule allows.
- [cola] One push per review round: batch the blocking findings, re-run the pair, push once; a gate PASS covers only the commit it reviewed.
- [cola] The progress comments, each PR's gate-dossier comment and the follow-up issue(s) are the batch's only tracker writes; a PR closes what it names.
- Every branch — integration or per-ticket — stays merge-commit-free and rebase-mergeable.

## Resume

[cola] Re-run `/implement-spec <spec>` after an interruption. The branch log and the tickets' and spec's progress comments — including their `blocking:` and `deferred:` lines — are the batch's state; the session's captured ticket sessions do not survive it:

- **Adopt the branch** (integration mode): resume only a branch whose every commit `origin/main` lacks carries a `Refs: #<n>` trailer naming one of this spec's tickets — a commit without one is not the batch's, and adopting the branch would ride it into the PR. A branch failing that check stops and asks instead of being resumed.
- **Adopt the PR** (both modes): a branch that already has an open PR adopts it and its `<!-- gate-dossier -->` comment (the marker is the comment's first line, so a review that quotes it is not the dossier; create one when none exists); never open a second PR or a second dossier. Rebuild the round count from the gate reviews already on the PR, deduplicated against the dossier, and the deferred list as the union of those reviews, the dossier, and the tickets'/spec's `deferred:` lines — the `blocking:` lines are re-checked, never turned into deferred items — then patch a comment that is behind them.
- **Per-ticket mode**: the spec's `## Landing` section names the mode and any merge grant (whose tickets it must name). A ticket is done when its PR is merged; without a grant it is done at its green-PR handover. The frontier is the first child whose PR is neither merged nor open, found with `gh pr list --search 'closes #<child>' --state all` — an open PR is adopted (the bullet above), never duplicated. **A PR whose dossier records a stop predicate is that ticket's handover: adopt it, never merge it under the grant** — the batch stops there for the user.
- **Windows**: a ticket's window is the commits carrying its `Refs: #<n>` trailer, with the base at the commit before the first of them — normally one contiguous run, because landings are linear. In per-ticket mode the window is that PR's `origin/main...HEAD`.
- **Tickets** (integration mode): a ticket is done only when its progress comment names this branch, names a commit still on the integration tip (`git merge-base --is-ancestor <sha> HEAD`), and that commit is the **last** one carrying the ticket's trailer — only then does the comment's review cover the whole window. A trailer-bearing commit *after* the comment is unreviewed work: review the extended window and replace the ticket's comment (never a second one), never re-dispatch over landed commits. A ticket with trailer commits but no comment covering them is landed but unreviewed: review its window and post the comment, not a new implementer. A ticket with neither is dispatched.
- **Adopt the follow-up**: before creating the deferred follow-up issue, search for `Deferred from #<pr>` with `--state all --limit 100` and adopt the one a prior run made, reopening it when it is closed; create only when none exists. Add the current deferred findings by reading the issue body, merging and deduplicating, then PATCHing the merged body — never by replacing it with only the new items.
- **Interleaved** (integration mode): when another ticket's commits sit between this ticket's (a fix that landed after a later ticket), no single run defines its diff — leave that ticket to the whole-branch pass rather than reconstructing a partial window, and name it in the dossier.
- **Interrupted fix round**: the sessions are gone — re-review the window with fresh reviewers (the findings resurface), then dispatch a fresh implementer with them.
- **Dirty tree or worktrees**: never start a ticket on a dirty tree, and never reuse a stale worktree — inspect and clean up before dispatching.
